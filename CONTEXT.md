# ChatDACS Context

ChatDACS is evolving into a Xiaoye-centered chatbot framework. The project keeps the existing plugin protocol and platform behavior stable while gradually deepening runtime modules behind small internal interfaces.

## Domain Terms

- **小夜**: The chatbot persona and product identity exposed to Web users, QQ groups, QQ Guild, Bilibili live rooms, Telegram, and future agent runtimes.
- **平台 Adapter**: A module that translates one external chat platform event into ChatDACS runtime calls, then formats the response back to that platform.
- **OneBot Provider**: An external or legacy protocol implementation that connects a QQ account to the QQ platform Adapter. NapCatQQ remains the recommended provider; SnowLuma is an explicit, independent integration path that is not started or accepted on a real account in this work. `external` keeps generic OneBot 11 compatibility and `go-cqhttp` is retained for legacy deployments. Providers do not switch automatically.
- **Official QQ Adapter**: The optional `qqOfficial` channel using Tencent's connector and Node.js SDK in the ChatDACS process. Its bot application identity and opaque openids are isolated from OneBot numeric QQ identities. Only reviewed, allowlisted plugins execute on this channel.
- **插件运行时**: The runtime that loads legacy plugins, matches commands, handles plugin toggles, protects execution with soft timeout, and normalizes plugin responses.
- **Web Session**: The Web socket connection module responsible for anonymous cookie-based user identification, user profile initialization, online-user count, location display, nickname fallback, and basic socket events. The browser reads the exact `ChatdacsID` cookie, percent-decodes consistently with server `cookie.parse` (retaining malformed encoding as raw text), and rebuilds missing/empty or reserved bot ID `0` values; unrelated cookies no longer block initialization or cause self-message duplication. CID is not an authentication/authorization credential or a new login system. Disconnect cleanup is registered once before asynchronous initialization; cancellation prevents late user creation, welcome messages and event registration, and releases the online count exactly once.
- **Web Message**: The Web socket message module responsible for sanitizing user text, persisting Web messages, broadcasting user messages, executing plugins, and falling through to chat replies only when no plugin handled the message. A handled but silent plugin response also stops fallback.
- **Web Upload**: The multipart-upload module asynchronously renames files and returns HTTP `201` JSON with a shared safe display name. It does not emit independent media broadcasts: LayIM's success callback sends the upload markup through the normal socket `message` flow exactly once. Upload-only messages are persisted and broadcast without invoking plugins or chat fallback. `static/uploadMedia.js` wraps the application parser to convert only strict local `/uploads/<32-hex-id>[.<extension>]` audio/video file markup to the existing player syntax for sender and receiver; external, malformed or mixed-text messages are not treated as upload-only. Upload content is not logged. The image endpoint rejects executable image formats; active non-media files such as HTML, SVG, JavaScript and XML remain download attachments protected by `nosniff` and a sandbox policy.
- **Web Render Boundary**: `static/renderSecurity.js` sanitizes the final HTML after LayIM expansion, using pinned DOMPurify `3.4.17` served from the same-origin `/vendor/purify.min.js` route via the local dependency, not a CDN. Missing, unsupported or throwing purification falls back to escaped text. Nicknames, typing/online status and settings values have separate text/attribute-escaping boundaries. Media URL delimiters are encoded before LayIM's video popup or image enlargement can interpolate them a second time. Normal layout, base64 images and relative audio/video URLs remain supported; user-supplied display `style`, `id`, `name` and event attributes are not accepted. Only validated audio/video controller attributes needed by LayIM survive.
- **Tray Notification Boundary**: User-triggered Windows system notifications use `execFile('msg.exe', [username, 'ChatDACS: ' + text], ...)`, preserving Unicode argv without a shell. The prefix keeps notification text out of msg.exe option syntax; tray notifications retain their original text. The system-message subprocess has `windowsHide: true`, `timeout: 5000` and a 64 KiB output buffer. Failures use fixed codes and distinguish partial delivery from full success; this does not claim all tray menu commands were migrated or that a real desktop accepted the notification.

## Current Architecture Direction

- Keep public behavior compatible first; deepen one module at a time.
- Prefer injected dependencies at seams so platform and Web flows can be tested without real OneBot, external APIs, native graphics, or live sockets.
- Keep the legacy plugin interface compatible: `插件名`, `指令`, `init`, and `execute` remain the author-facing contract.
- Do not treat Web-only local configuration as product default; use tests and smoke scripts for local verification.
- Keep QQ protocol implementations outside ChatDACS ownership. The Adapter depends on the OneBot 11 contract, while startup probes and integration guides handle provider-specific setup.
- `System.ERROR_NOTIFY_GROUP_ID` is optional and must be a quoted digits-only group ID. Its runtime default is `undefined`: no error-group notification is sent unless it is configured and OneBot is enabled. It replaces the old hard-coded group; notifications carry fixed safe codes, never the original error, stack or user payload.
- HTTP `EADDRINUSE` retries after 10 seconds without calling `close()` or disposing adapters. Other listen errors report fixed safe codes and do not retry. An explicit final HTTP close cancels retries and still triggers index-owned adapter/process-handler cleanup.

## Main Entry and Lifecycle

`main({configPath, pluginDependencyOverrides, checkUpdates = true} = {})` uses the existing configuration, dependency and update behavior when options are omitted, and returns `{http, io, stop}`. `pluginDependencyOverrides` replaces named plugin dependencies without bypassing the real main/migration/plugin startup sequence. `checkUpdates: false` disables the update check for an explicitly isolated test; it does not by itself make a normal configuration safe to run.

A platform startup/connection failure reports its fixed platform code and leaves Web and other platforms running; it does not switch providers or pretend that platform is ready. Configuration/database failures and invalid controller contracts are not silently downgraded. Default logging has only Console and the two cwd-local files `error.log` and `combined.log`; there is no default Winston HTTP transport or log POST to localhost:80. This is a logging boundary, not a promise that all application networking is disabled.

Set `CHATDACS_DB_PATH` before requiring index or database modules: the Sequelize storage path is captured at module load. `System.WEB_HOST` is optional; omission keeps the previous listen binding, not an implied loopback restriction. The shadow smoke uses an isolated fixture configuration/database, fixed `127.0.0.1` host and ephemeral port, substitutes the tray dependency, disables update checks and guards against external activity.

The idempotent asynchronous `stop()` coordinates QQ/official QQ/Guild/Bilibili/Telegram controllers, socket/HTTP shutdown, process-error handler disposal and SQL connection closure. Bilibili and Telegram have mock coverage for safe stop and suppressing output from work that completes after stop. Real tray resources and automatically launched go-cqhttp child processes are outside this ownership; do not equate graceful shadow shutdown with whole-process or all-platform acceptance. Guild's embedded OneBot sender now uses the shared authenticated HTTP client and URL-encoded sender path rather than hand-built reply URLs; real Guild delivery still needs separate acceptance.

`npm run smoke:startup` executes the real-main shadow flow, including HTTP, session, plugin/chat and graceful stop checks. It is wired into `npm run verify:release`, CI production validation and bundled-runtime validation. The main worker's normal/degrade/logger checks passed for its frozen scope; that is not a completed six-platform cloud run or the pending full merged-candidate acceptance.

## OneBot Integration Boundary

Keep SnowLuma and NapCat provider configuration, credentials and login data separate; selecting or probing one does not install, start or fall back to the other. The SnowLuma v2.4.0 source contract uses `networks`, `enabled`, `accessToken` and `messageFormat`, not NapCat's `network`, `enable`, `token` and `messagePostFormat`. The provider/schema and signed-webhook details are owned by the OneBot integration worker and documented in `integrations/snowluma/README.md`. SnowLuma remains code-only here, with no service startup, QQ login or live message-delivery acceptance.

The integration talks HTTP to a separately deployed SnowLuma; ChatDACS does not bundle its source, program or native components. Upstream describes its [v2.4.0 license](https://github.com/SnowLuma/SnowLuma/blob/v2.4.0/LICENSE) as source-available and non-commercial, not OSI open source. Check upstream terms before deployment, commercial use or redistribution. Relative `ONE_BOT_CREDENTIALS_FILE` paths resolve from process cwd, not the YAML directory, matching the main runtime.

The shared Express JSON parser copies the verification buffer to `req.rawBody` without changing the default `100kb` body limit or parsed `req.body`. This supports the SnowLuma `X-Signature: sha1=<hex>` contract, computed as HMAC-SHA1 of the raw payload bytes using the access token. Do not sign a reserialized JSON object, log the raw body or expose credentials.
